# FPSMaster 性能优化路线图

本文档规划下一阶段的性能工作。目标项目为 Edge 1.8.9；涉及通用策略时，再单独评估是否同步到 Nova。

## 一、目标与原则

性能工作的首要目标是改善真实游戏负载下的帧时间和稳定性，而不只是增加设置数量。

- 优先减少重复 CPU 工作，其次处理 p95、p99 和最大帧时间中的长尾卡顿。
- 不以单次 FPS 峰值作为结论。所有核心优化必须通过可重复的基线/实验组对照。
- 画质裁剪项必须默认关闭，并在设置说明中明确其视觉影响。
- 实验功能不得在普通会话中改变行为；定价探针只在 benchmark 模式下启用。
- 每项优化独立提交、独立开关、独立验证，避免多个变量混在一次测试中。

## 二、统一验收标准

### 2.1 Benchmark 方法

每个核心优化至少覆盖以下负载：

1. 固定录像场景：用于比较相同相机轨迹和实体负载。
2. 对应压力场景：人为放大目标路径，确认机制确实生效。
3. 普通单人世界：检查区块加载、世界切换和资源重载等生命周期。

每个实验使用相同 JVM 参数、分辨率、图形设置和场景，基线与实验组交错运行。报告至少记录：

- FPS 与 CPU 帧时间 p50、p95、p99、max；
- 目标 section 的 CPU 时间和调用次数；
- GC 次数、GC 时间以及与目标有关的工作量计数器；
- 截图差异、控制台错误和人工观察到的异常。

### 2.2 进入实现的门槛

探针阶段满足以下任一条件后，核心优化才进入正式实现：

- 目标路径在真实负载中占 CPU 帧时间至少 3%；
- 目标路径在压力场景中造成可稳定复现的 p99 或 max 卡顿；
- 已有对照证明简单方案带来至少 5% 的稳定收益；
- 该项能以很小的改动消除已确认的分配或阻塞，并且不会改变游戏画面。

低成本画质裁剪项不受此门槛限制，因为它们是用户主动选择的性能旋钮，不作为同画面优化成果统计。

### 2.3 完成标准

核心优化只有同时满足以下条件才算完成：

- 目标计数器证明优化路径被实际命中；
- 至少三组有效配对测试，结果方向一致；
- 没有新增可见错误、世界生命周期错误或后台任务泄漏；
- 默认设置合理，关闭功能后恢复原版行为；
- 文档记录测试场景、原始结果位置、结论和已知限制。

## 三、阶段排期

阶段是依赖顺序，不绑定具体发布日期。每个阶段完成验收后再进入下一阶段；低风险项可以在阶段内并行开发，但仍需分别测试和提交。

| 阶段 | 工作项 | 主要产物 | 退出条件 |
|---|---|---|---|
| 0 | 基线与探针 | 可见区块构建、活动区块、实体碰撞、光照、纹理和 GUI 的计时/计数 | 能回答各路径在真实负载中的占比 |
| 1 | 动态区块更新预算；低成本画质旋钮 | 自适应区块预算；植被/栅栏/头颅/盔甲架隐藏；贴图分辨率设置 | 功能独立可控，区块空洞和视觉影响已验证 |
| 2 | 可见区块遍历实验 | 细分探针、保守复用原型、完整失效验证 | 稳定收益达到门槛且无错误复用 |
| 3 | 活动区块集合实验；快速实体碰撞 | 重建探针；碰撞查询优化 | tick CPU 或帧时间收益达到门槛 |
| 4 | 异步光照 | 有版本校验的任务模型和压力测试 | 无跨世界写入、漏光和竞态，p99 改善明确 |
| 5 | 纹理加载临时数据优化 | 资源重载期间的分配与耗时基准 | 分配或加载卡顿下降且无纹理损坏 |
| 候选 | GUI 静态层预渲染 | 仅 benchmark 结论；满足门槛后再立实现任务 | 当前不承诺实现 |

## 四、详细工作项

### 4.1 可见区块遍历实验

#### 目标

确认 `RenderGlobal.setupTerrain` 在相机持续小幅移动时重复执行的可见区块遍历是否值得进一步减少。

Forge 1.8.9 已经通过 `displayListEntitiesDirty` 缓存 `renderInfos`：相机完全静止且没有待更新区块时，本来就不会重建列表。因此本项不是从零增加缓存，也不能在方法入口直接取消整个调用。`setupTerrain` 后半段还负责清理 dispatcher 更新状态、收集 dirty chunk，以及同步重建玩家附近的区块，整个方法提前返回会破坏这些行为。

#### 阶段 0：先定价

在现有 `setupTerrain` section timing 基础上补充：

- 每帧调用次数和总 CPU 时间，并把方法拆成相机更新、可见列表 BFS、dirty chunk 收集三段；
- `displayListEntitiesDirty` 为 true/false 的帧数；
- BFS 遍历或加入的 RenderChunk 数量；
- 脏状态来自相机位移、旋转、待更新区块还是外部 `setDisplayListEntitiesDirty`；
- 小幅移动/旋转时的连续重建次数，以及放宽阈值后理论可复用的帧数。

#### 实现边界

只有探针证明 BFS 是主要成本后，才建立只抑制 BFS 重建的原型。不得取消整个 `setupTerrain`。原型需要保留每帧的 render container 初始化和 dirty chunk 收集，并为可见列表单独维护明确的 generation/dirty 状态。

以下事件至少应强制重建可见列表：

- 相机跨区块或超过确定的位移/旋转阈值；
- FOV、缩放、窗口比例、渲染距离或投影矩阵变化；
- 区块加载、卸载、重建或可见性数据变化；
- `ViewFrustum` 位置更新、世界加载/卸载、维度切换或资源重载；
- 调用方明确要求强制更新。

目标 BFS、容器信息类和 dirty 赋值都位于同一个长方法内部，普通 HEAD/RETURN 注入不足以安全替换该段逻辑。正式实现前必须在映射后的 Forge 方法上验证可用的 slice/redirect 注入点；如果只能覆盖整个方法，则默认停止该方案，除非收益足以承担长期维护成本。

#### 验收

- 持续缓慢移动/旋转场景中 BFS 执行次数和 `setupTerrain` CPU 时间显著改善；
- 快速旋转、缩放、传送、破坏/放置方块和切换视距时不出现缺块；
- 真实录像的配对测试达到统一进入/完成门槛，否则只保留探针结论，不合入实现。

### 4.2 动态区块更新预算

#### 目标

在玩家移动时控制区块重建吞吐，在玩家静止后加快清理积压，替代始终固定的一秒累计编译额度。

#### 第一版范围

当前实现位于 `ChunkRenderDispatcher.getNextChunkUpdate`，按 `RenderChunk.renderChunksUpdated` 的一秒累计值让 worker 线程每次休眠 50ms；它不是每帧提交预算。与此同时，`RenderGlobal.updateChunks` 已经使用 `finishTimeNano` 控制主线程提交时间。因此第一版只调整 worker 编译额度，不重复实现主线程帧预算。

基于现有 `LimitChunks` 和 `ChunkUpdateLimit` 做简单二档策略：

- 移动或快速转向：使用用户配置的基础预算；
- 静止：使用基础预算的两倍；
- 主线程继续沿用原版 `finishTimeNano` 截止时间。

由主线程计算玩家是否移动或快速转向，并把当前额度写入一个 worker 可见的轻量状态；worker 注入点只读取额度。还需要把现有固定 50ms 轮询改成可及时响应状态变化的等待方式，避免静止额度提高后仍要等待完整睡眠周期。

第一版不引入 PID 控制器、自动硬件分级或复杂预测。

#### 验收

- 记录每帧提交数、完成数、待处理数和区块更新时间；
- 比较移动中的 p95/p99，以及停止移动后清空积压所需时间；
- 不允许区块永久不更新、队列持续增长或卸载后的任务继续执行；
- 若自适应策略没有胜过现有固定预算，保留当前实现。

### 4.3 活动区块集合重建实验

#### 目标

减少 `World.setActivePlayerChunksAndCheckLight` 每 tick 清空并重建 `activeChunkSet` 产生的 CPU 和短命对象。

客户端 `playerEntities` 不一定只有本地玩家，直接只以本地玩家 chunk 坐标作为缓存键会改变多人场景语义。因此目前不能确定为“玩家未跨 chunk 就复用”，必须先确认远端玩家对该集合的实际影响和调用成本。

#### 定价探针

- 目标方法每 tick 的调用次数和 CPU 时间；
- 每次遍历和加入的 chunk 数；
- `playerEntities` 数量、所有玩家的 chunk 坐标变化，以及集合内容实际发生变化的 tick 比例；
- 集合容量变化和可归因的分配量。

#### 实现与失效条件

- 若确认只需本地玩家，才以本地玩家 chunk 坐标作为缓存键；否则缓存键必须覆盖所有参与玩家的 chunk 坐标；
- persistent chunks、视距、世界/维度和参与玩家集合变化时失效；
- 世界卸载时释放集合引用；
- 即使复用集合，也必须保留该方法后半段每 tick 的随机 `checkLight`，不能取消整个方法。

实现入口预计为 `World.setActivePlayerChunksAndCheckLight` 的局部构建段。若 Mixin 无法只替换构建段而必须覆盖整个 World 方法，则先保留探针，不为了小收益引入覆盖。

#### 验收

固定站立、缓慢行走、传送、切维度和改变视距均与原行为一致；若目标路径低于测量噪声，不实现缓存。

### 4.4 快速实体碰撞查询

#### 目标

减少实体密集场景中碰撞查询扫描的无关实体数量和重复工作，优先改善客户端 tick CPU。

#### 定价探针

对实体 AABB 查询记录：

- 每 tick 查询次数和调用者分布；
- 扫描的 chunk/section 数；
- 检查实体数、返回实体数和过滤比例；
- 查询 CPU p50、p95、p99；
- 同 tick 重复或高度重叠查询的比例。

#### 实现顺序

1. 先利用现有 chunk/section 实体容器缩小扫描范围。
2. 消除已确认的同 tick 重复查询或中间集合分配。
3. 只有现有分区仍是瓶颈时，才评估额外空间索引。

不在第一版引入全局空间树，也不缓存跨 tick 的碰撞结果。

源码确认原版已经按 X/Z chunk 和 16 格高的 `entityLists` section 扫描。因此“增加分区”不是可直接实施的优化。探针应放在 `World.getEntitiesInAABBexcluding` 和 `Chunk.getEntitiesWithinAABBForEntity`；后续方案只能针对已测出的无关实体扫描、返回列表分配或重复查询，不能预设一定需要新的空间索引。

#### 验收

- 普通、实体密集和大量掉落物场景均通过；
- 碰撞、推挤、骑乘、方块边缘移动和实体卸载行为一致；
- 压力场景必须显著减少扫描量，真实场景必须达到统一收益门槛。

### 4.5 异步光照

#### 目标

把已确认的光照传播长任务移出客户端主线程，降低区块更新时的 p99 和最大帧时间。

#### 阶段 0：先确认瓶颈

记录光照更新调用次数、处理节点数、每 tick CPU 时间、队列长度，以及最慢帧中光照 section 的占比。没有明确长尾证据时不进入实现。

#### 实现约束

- 后台线程只计算结果，不直接修改已卸载或版本已变化的世界状态；
- 任务携带 world generation、chunk generation 和光照版本；
- 主线程提交前重新校验版本，过期结果直接丢弃；
- chunk 卸载、世界切换和客户端退出必须取消或使任务失效；
- 第一版使用有界队列和固定工作线程数，不做自动线程调优；
- 不通过同步等待后台任务来伪装异步。

#### 验收

- 压力场景覆盖连续放置/破坏光源、跨 chunk 传播、快速飞行和世界切换；
- 不出现漏光、闪烁、陈旧结果覆盖、并发异常或退出后残留线程；
- p99/max 明确改善，平均 FPS 下降不得超过噪声范围；
- 若正确性无法用小改动保证，停止实现并保留同步路径。

### 4.6 纹理加载临时数据优化

#### 目标

减少资源加载和纹理图集构建过程中的临时像素数组、mipmap 数据和复制成本，改善资源包切换卡顿。

Forge 1.8.9 的 `TextureUtil` 已经持有并复用一个静态 4,194,304-int direct buffer，普通 `uploadTextureSub` 不会为每次上传重新分配 direct buffer。因此不实现新的上传缓冲池。

#### 定价探针

- 纹理上传次数、字节数和单次/总耗时；
- `uploadTextureImageSubImpl` 的临时 `int[]` 分配量；
- mipmap 生成和图像像素提取耗时；
- 资源包加载、切换和动态图场景中的 GC 情况。

#### 第一版范围

- 若探针确认 `BufferedImage` 上传临时数组是显著来源，只复用该堆上 `int[]`；
- 保留原版静态 direct buffer 和分块上传逻辑；
- mipmap 或图像解码只有在各自 section 达到门槛后才单独立项；
- 不把资源加载优化宣传为游戏内平均 FPS 优化。

#### 验收

- 资源包加载、重复切换、动画纹理和超大贴图均无损坏；
- 临时数组分配显著减少，加载耗时或 GC 指标至少一项稳定改善；
- 可复用堆数组不得因一次异常资源永久保留过大内存。

## 五、低成本画质与内容裁剪

这些设置通过少绘制或降低资源精度换取性能，不应和同画面优化混为一谈。统一放在 Performance 模块的视觉裁剪分组，默认关闭并提供明确说明。

### 5.1 方块与实体隐藏

计划加入以下独立开关：

- `HideTallGrass`：隐藏高草；
- `HideDoubleTallGrass`：隐藏双高草；
- `HideFlowers`：隐藏花；
- `HideDoubleTallFlowers`：隐藏双高花；
- `HideFences`：隐藏栅栏；
- `HideFenceGates`：隐藏栅栏门；
- `HideSkulls`：隐藏头颅 block entity；
- `HideArmorStands`：跳过盔甲架实体渲染。

实现入口已经可以确定：

- 植被和栅栏在 `BlockRendererDispatcher.renderBlock` 的 HEAD 按 `IBlockState.getBlock()` 过滤并返回 `false`，只影响区块网格生成；
- 盔甲架在 `RenderManager.doRenderEntity` 的现有 HEAD 注入中按 `EntityArmorStand` 返回 `false`；
- 头颅在 `TileEntityRendererDispatcher.renderTileEntity` 的现有 HEAD 注入中按 `TileEntitySkull` 取消；
- 开关变化后仅触发必要的区块重建；
- 头颅和盔甲架只跳过渲染，不删除实体或 block entity；
- `HideArmorStands` 与现有只隐藏名称的 `IgnoreStands` 明确区分，避免用户误解；
- 所有选项默认关闭，并提示可能隐藏服务器标记、装饰或必要信息。

验收覆盖资源包模型、世界重载、运行中开关，以及栅栏连接/门开合后区块正确重建。

### 5.2 贴图分辨率限制（已实现，改为采样方案）

**原方案（缩放图片）已废弃。** 原计划提供最大边长档位并缩放图片，但 `TextureAtlasSprite.loadSprite` 按图片宽度解析动画帧数，缩放后每个动画贴图的帧布局都会被改写；而拦截 `TextureUtil.readBufferedImage` 又会连 GUI、字体、光照贴图和动态纹理一起误伤。这两个问题都无解，只要动的是像素。

**现方案：只动采样，不动像素。** `GL_TEXTURE_MIN_LOD` 在放大/缩小判定**之前**钳制 LOD，所以把下限设为 2，贴在镜头前的方块也会从 mip level 2 采样 —— 每档边长减半。图集本身完全不变：同样的图片、同样的拼接、同样的帧布局、同样的纹理对象。

这个方案还自带了原方案要靠过滤器维护的隔离性：方块图集是原版唯一带 mipmap 链分配的纹理（`TextureUtil.allocateTextureImpl(id, mipmapLevels, w, h)`），GUI、字体、光照贴图和动态纹理都是单层分配，**结构上**够不着 mipmap 设置。

档位为 `Default` / `Half` / `Quarter` / `Eighth` / `Sixteenth`，索引即 LOD 下限。命名按"相当于多少倍率的贴图"而不是像素数，因为同一档在 16x 和 512x 资源包上必须都成立。

实现要点：

- `TextureUtil.allocateTextureImpl` 只在图集分配时写一次 LOD 范围，`setTextureBlurMipmap` 只碰 MIN/MAG_FILTER，所以不需要每帧重设；但**资源重载会重新分配纹理并把 LOD 范围写回默认值**，因此在 `TextureMap.loadTextureAtlas` 返回处重新应用。
- 上限钳制到图集实际的 `mipmapLevels`，它不等于游戏的 Mipmap Levels 设置 —— `loadTextureAtlas` 在图集不是足够大的二次幂时会自行下调。
- 游戏的 Mipmap Levels 设为 0 时本功能无效（没有更粗的层可退），此时记一条日志，否则和功能坏掉无法区分。

验收记录截图差异、显存近似占用和资源重载后是否仍然生效；默认必须为 `Default`。

## 六、GUI 静态层预渲染候选

该项当前只进入 benchmark backlog，不承诺实现。

### 6.1 待回答的问题

- HUD、聊天、计分板、Tab 列表和客户端组件分别占用多少 CPU/GPU 帧时间；
- 静止画面中有多少 GUI 内容能够跨帧复用；
- 把静态层渲染到纹理后，合成 draw call、FBO 切换和脏矩形维护是否反而更贵；
- 与模糊、动态字体、动画、缩放和截图功能是否兼容。

### 6.2 实现门槛

只有同时满足以下条件才建立正式实现任务：

- GUI section 在目标场景中占 CPU 或 GPU 帧时间至少 5%；
- 可复用静态内容占 GUI 成本的大部分；
- benchmark 原型在至少两个分辨率上带来稳定正收益；
- 更新频繁的聊天、动画和调试界面不会导致每帧重新生成整张缓存。

若进入实现，第一版只缓存单个边界清晰、更新频率低的组件，不做全屏 GUI 缓存框架。
