# FPSMaster 性能优化路线图

本文档规划下一阶段的性能工作。目标项目为 Edge 1.8.9；涉及通用策略时，再单独评估是否同步到 Nova。

## 一、目标与原则

性能工作的首要目标是改善真实游戏负载下的帧时间和稳定性，而不只是增加设置数量。

- 优先减少重复 CPU 工作，其次处理 p95、p99 和最大帧时间中的长尾卡顿。
- 不以单次 FPS 峰值作为结论。所有核心优化必须通过可重复的基线/实验组对照。
- 画质裁剪项必须默认关闭，并在设置说明中明确其视觉影响。
- 实验功能不得在普通会话中改变行为；定价探针只在 benchmark 模式下启用。
- 每项优化独立提交、独立开关、独立验证，避免多个变量混在一次测试中。

## 二、统一验收标准

### 2.0 五分钟闸门（常规验证的默认档）

**一次小改动的验证不得超过 5 分钟。** 实测单次客户端启动的固定开销是 **48s**（JVM + Forge + mixin 初始化 + 世界加载 + settle），场景本身只占几十秒，所以 5 分钟的预算换算下来就是**四次启动**。

默认命令：

```powershell
.enchmark
un-series.ps1 -Scenario text-dense-quick -Runs 1 -DiscardPasses 1 `
    -Variants ([ordered]@{ off = @{ 'X' = $false }; on = @{ 'X' = $true } })
```

四次启动 = 每个变体一轮丢弃 + 一轮测量，实测约 4.5 分钟。`text-dense-quick` 的截图放在预热段内（camera t=1000/3000/5000，测量窗口 t=7000 才打开），所以**像素闸门是白拿的** —— 回读会打断管线，不能从它要陪跑的那份时间里出。

**这一档是筛子，不是判决。** 每变体只有一轮，看不见轮间方差，而本项目已经三次把轮间噪声读成效果。规则：

- 方向不明或区间可能重叠 → 升级到长系列（`-Runs 3 -DiscardPasses 2`，约 20 分钟）
- 要改默认值、或要写进结论 → 必须有长系列背书
- 只是想知道"这个改动是不是明显反向" → 五分钟档够了

**这一档的噪声地板是逐 section 的，差别巨大。** 同配置对同配置的空对照（`nullcontrol`，两次启动）实测：

| 同配置两轮 | a | b | 离散 |
|---|---:|---:|---:|
| avg fps | 474.7 | 374.0 | **21%** |
| `frameTotal` p50 | 1416 us | 1546 us | 9.2% |
| `terrainSetup` | 370 us | 489 us | **32%** |
| `entities` | 704 us | 736 us | 4.5% |
| `hud` | 53 us | 55 us | **3.8%（2us）** |

所以这一档：

- **对 `hud` 级的改动可用** —— 2us 地板，字体那两项合并的 −12us 是它的六倍
- **对 `terrainSetup`、整帧、avg fps 不可用** —— 地板比大多数候选效果还大，读出来的任何方向都是运气

噪声估计本身只有一对样本（n=1），别当精确值用；它的作用是把"哪些 section 值得在这一档上看"这件事定下来。

**像素闸门对改变帧率的优化有结构性缺陷。** 手臂旋转与实体动画都是朝目标值平滑插值的，插值步数取决于跑了多少帧；帧率一变，它们就停在不同相位。实测：同配置空对照 363 像素，off/on 6102 像素，而其中 HUD 文字区域两者都是 0。**判定必须配合区域定位来读**，只看总百分比会连续得出错误结论。不加区域白名单 —— 那会让闸门同时不再能抓缺地形，而缺地形会让帧时间变好、时间报告分辨不出来，那是它存在的首要理由。

**像素闸门在这一档是免费的，但对截图时刻敏感。** 截图放在 t=1000 时，同一份构建的两轮在第一人称手臂上差 5877 像素（0.552%），越过 0.5% 门限 —— 手持物品的装备动画那时还在插值。移到 t=3200/4500/5800 后空对照三张全过（0.028% / 0.092% / 0.192%），最差的一张仍有 2.6 倍余量。**新增截图时刻必须先跑空对照**，否则闸门会以与被测改动无关的理由否掉每一个候选。

### 2.1 Benchmark 方法

每个核心优化至少覆盖以下负载：

1. 固定录像场景：用于比较相同相机轨迹和实体负载。
2. 对应压力场景：人为放大目标路径，确认机制确实生效。
3. 普通单人世界：检查区块加载、世界切换和资源重载等生命周期。

每个实验使用相同 JVM 参数、分辨率、图形设置和场景，基线与实验组交错运行。报告至少记录：

- FPS 与 CPU 帧时间 p50、p95、p99、max；
- 目标 section 的 CPU 时间和调用次数；
- GC 次数、GC 时间以及与目标有关的工作量计数器；
- 截图差异、控制台错误和人工观察到的异常。

### 2.2 进入实现的门槛

探针阶段满足以下任一条件后，核心优化才进入正式实现：

- 目标路径在真实负载中占 CPU 帧时间至少 3%；
- 目标路径在压力场景中造成可稳定复现的 p99 或 max 卡顿；
- 已有对照证明简单方案带来至少 5% 的稳定收益；
- 该项能以很小的改动消除已确认的分配或阻塞，并且不会改变游戏画面。

低成本画质裁剪项不受此门槛限制，因为它们是用户主动选择的性能旋钮，不作为同画面优化成果统计。

### 2.4 门槛不适用于"无代价"的改动

**这条比上面的门槛优先。** 开发机的 CPU 和 GPU 都很强，很多纯 CPU 侧的削减在它上面落在噪声里 —— 但客户端的用户不都在这样的机器上跑。

一个改动如果同时满足：

- 不改变画面（同画面）；
- 不引入新的失败模式；
- 实现不复杂、不需要维护额外的不变量；

那么**即使在开发机上测不出收益也应当做**，只要它的方向为正。理由是瓶颈会移动：减少每帧的 draw call、矩阵调用、分配和 per-call 开销，在一台 CPU 受限的机器上是线性收益，而在一台 GPU 受限的机器上只是测不出来 —— 测不出来不等于没有。

反过来，凡是需要**用画面或正确性换性能**的（视觉裁剪、可见列表复用、区块限流），门槛照旧，而且要更严：它们的代价在所有机器上都是真的。

判断一项改动落在哪一边，问三个问题：它删掉的是每帧固定的 CPU 工作吗？它在最坏情况下画出的东西和原版一样吗？关掉它是否完全回到原版行为？三个都是，就做。

### 2.3 完成标准

核心优化只有同时满足以下条件才算完成：

- 目标计数器证明优化路径被实际命中；
- 至少三组有效配对测试，结果方向一致；
- 没有新增可见错误、世界生命周期错误或后台任务泄漏；
- 默认设置合理，关闭功能后恢复原版行为；
- 文档记录测试场景、原始结果位置、结论和已知限制。

## 三、阶段排期

阶段是依赖顺序，不绑定具体发布日期。每个阶段完成验收后再进入下一阶段；低风险项可以在阶段内并行开发，但仍需分别测试和提交。

| 阶段 | 工作项 | 主要产物 | 退出条件 |
|---|---|---|---|
| 0 | 基线与探针 | 可见区块构建、活动区块、实体碰撞、光照、纹理和 GUI 的计时/计数 | 能回答各路径在真实负载中的占比 |
| 1 | 动态区块更新预算；低成本画质旋钮 | 自适应区块预算；植被/栅栏/头颅/盔甲架隐藏；贴图分辨率设置 | 功能独立可控，区块空洞和视觉影响已验证 |
| 2 | 可见区块遍历实验 | 细分探针、保守复用原型、完整失效验证 | 稳定收益达到门槛且无错误复用 |
| 3 | 活动区块集合实验；快速实体碰撞 | 重建探针；碰撞查询优化 | tick CPU 或帧时间收益达到门槛 |
| 4 | 异步光照 | 有版本校验的任务模型和压力测试 | 无跨世界写入、漏光和竞态，p99 改善明确 |
| 5 | 纹理加载临时数据优化 | 资源重载期间的分配与耗时基准 | 分配或加载卡顿下降且无纹理损坏 |
| 候选 | GUI 静态层预渲染 | 仅 benchmark 结论；满足门槛后再立实现任务 | 当前不承诺实现 |

## 四、详细工作项

### 4.1 可见区块遍历实验

#### 目标

确认 `RenderGlobal.setupTerrain` 在相机持续小幅移动时重复执行的可见区块遍历是否值得进一步减少。

Forge 1.8.9 已经通过 `displayListEntitiesDirty` 缓存 `renderInfos`：相机完全静止且没有待更新区块时，本来就不会重建列表。因此本项不是从零增加缓存，也不能在方法入口直接取消整个调用。`setupTerrain` 后半段还负责清理 dispatcher 更新状态、收集 dirty chunk，以及同步重建玩家附近的区块，整个方法提前返回会破坏这些行为。

#### 阶段 0：先定价

在现有 `setupTerrain` section timing 基础上补充：

- 每帧调用次数和总 CPU 时间，并把方法拆成相机更新、可见列表 BFS、dirty chunk 收集三段；
- `displayListEntitiesDirty` 为 true/false 的帧数；
- BFS 遍历或加入的 RenderChunk 数量；
- 脏状态来自相机位移、旋转、待更新区块还是外部 `setDisplayListEntitiesDirty`；
- 小幅移动/旋转时的连续重建次数，以及放宽阈值后理论可复用的帧数。

#### 实现边界

只有探针证明 BFS 是主要成本后，才建立只抑制 BFS 重建的原型。不得取消整个 `setupTerrain`。原型需要保留每帧的 render container 初始化和 dirty chunk 收集，并为可见列表单独维护明确的 generation/dirty 状态。

以下事件至少应强制重建可见列表：

- 相机跨区块或超过确定的位移/旋转阈值；
- FOV、缩放、窗口比例、渲染距离或投影矩阵变化；
- 区块加载、卸载、重建或可见性数据变化；
- `ViewFrustum` 位置更新、世界加载/卸载、维度切换或资源重载；
- 调用方明确要求强制更新。

目标 BFS、容器信息类和 dirty 赋值都位于同一个长方法内部，普通 HEAD/RETURN 注入不足以安全替换该段逻辑。正式实现前必须在映射后的 Forge 方法上验证可用的 slice/redirect 注入点；如果只能覆盖整个方法，则默认停止该方案，除非收益足以承担长期维护成本。

#### 验收

- 持续缓慢移动/旋转场景中 BFS 执行次数和 `setupTerrain` CPU 时间显著改善；
- 快速旋转、缩放、传送、破坏/放置方块和切换视距时不出现缺块；
- 真实录像的配对测试达到统一进入/完成门槛，否则只保留探针结论，不合入实现。

### 4.2 动态区块更新预算

#### 目标

在玩家移动时控制区块重建吞吐，在玩家静止后加快清理积压，替代始终固定的一秒累计编译额度。

#### 第一版范围

当前实现位于 `ChunkRenderDispatcher.getNextChunkUpdate`，按 `RenderChunk.renderChunksUpdated` 的一秒累计值让 worker 线程每次休眠 50ms；它不是每帧提交预算。与此同时，`RenderGlobal.updateChunks` 已经使用 `finishTimeNano` 控制主线程提交时间。因此第一版只调整 worker 编译额度，不重复实现主线程帧预算。

基于现有 `LimitChunks` 和 `ChunkUpdateLimit` 做简单二档策略：

- 移动或快速转向：使用用户配置的基础预算；
- 静止：使用基础预算的两倍；
- 主线程继续沿用原版 `finishTimeNano` 截止时间。

由主线程计算玩家是否移动或快速转向，并把当前额度写入一个 worker 可见的轻量状态；worker 注入点只读取额度。还需要把现有固定 50ms 轮询改成可及时响应状态变化的等待方式，避免静止额度提高后仍要等待完整睡眠周期。

第一版不引入 PID 控制器、自动硬件分级或复杂预测。

#### 验收

- 记录每帧提交数、完成数、待处理数和区块更新时间；
- 比较移动中的 p95/p99，以及停止移动后清空积压所需时间；
- 不允许区块永久不更新、队列持续增长或卸载后的任务继续执行；
- 若自适应策略没有胜过现有固定预算，保留当前实现。

### 4.3 活动区块集合重建实验

#### 目标

减少 `World.setActivePlayerChunksAndCheckLight` 每 tick 清空并重建 `activeChunkSet` 产生的 CPU 和短命对象。

客户端 `playerEntities` 不一定只有本地玩家，直接只以本地玩家 chunk 坐标作为缓存键会改变多人场景语义。因此目前不能确定为“玩家未跨 chunk 就复用”，必须先确认远端玩家对该集合的实际影响和调用成本。

#### 定价探针

- 目标方法每 tick 的调用次数和 CPU 时间；
- 每次遍历和加入的 chunk 数；
- `playerEntities` 数量、所有玩家的 chunk 坐标变化，以及集合内容实际发生变化的 tick 比例；
- 集合容量变化和可归因的分配量。

#### 实现与失效条件

- 若确认只需本地玩家，才以本地玩家 chunk 坐标作为缓存键；否则缓存键必须覆盖所有参与玩家的 chunk 坐标；
- persistent chunks、视距、世界/维度和参与玩家集合变化时失效；
- 世界卸载时释放集合引用；
- 即使复用集合，也必须保留该方法后半段每 tick 的随机 `checkLight`，不能取消整个方法。

实现入口预计为 `World.setActivePlayerChunksAndCheckLight` 的局部构建段。若 Mixin 无法只替换构建段而必须覆盖整个 World 方法，则先保留探针，不为了小收益引入覆盖。

#### 验收

固定站立、缓慢行走、传送、切维度和改变视距均与原行为一致；若目标路径低于测量噪声，不实现缓存。

### 4.4 快速实体碰撞查询

#### 目标

减少实体密集场景中碰撞查询扫描的无关实体数量和重复工作，优先改善客户端 tick CPU。

#### 定价探针

对实体 AABB 查询记录：

- 每 tick 查询次数和调用者分布；
- 扫描的 chunk/section 数；
- 检查实体数、返回实体数和过滤比例；
- 查询 CPU p50、p95、p99；
- 同 tick 重复或高度重叠查询的比例。

#### 实现顺序

1. 先利用现有 chunk/section 实体容器缩小扫描范围。
2. 消除已确认的同 tick 重复查询或中间集合分配。
3. 只有现有分区仍是瓶颈时，才评估额外空间索引。

不在第一版引入全局空间树，也不缓存跨 tick 的碰撞结果。

源码确认原版已经按 X/Z chunk 和 16 格高的 `entityLists` section 扫描。因此“增加分区”不是可直接实施的优化。探针应放在 `World.getEntitiesInAABBexcluding` 和 `Chunk.getEntitiesWithinAABBForEntity`；后续方案只能针对已测出的无关实体扫描、返回列表分配或重复查询，不能预设一定需要新的空间索引。

#### 验收

- 普通、实体密集和大量掉落物场景均通过；
- 碰撞、推挤、骑乘、方块边缘移动和实体卸载行为一致；
- 压力场景必须显著减少扫描量，真实场景必须达到统一收益门槛。

### 4.5 异步光照

#### 目标

把已确认的光照传播长任务移出客户端主线程，降低区块更新时的 p99 和最大帧时间。

#### 阶段 0：先确认瓶颈

记录光照更新调用次数、处理节点数、每 tick CPU 时间、队列长度，以及最慢帧中光照 section 的占比。没有明确长尾证据时不进入实现。

#### 实现约束

- 后台线程只计算结果，不直接修改已卸载或版本已变化的世界状态；
- 任务携带 world generation、chunk generation 和光照版本；
- 主线程提交前重新校验版本，过期结果直接丢弃；
- chunk 卸载、世界切换和客户端退出必须取消或使任务失效；
- 第一版使用有界队列和固定工作线程数，不做自动线程调优；
- 不通过同步等待后台任务来伪装异步。

#### 验收

- 压力场景覆盖连续放置/破坏光源、跨 chunk 传播、快速飞行和世界切换；
- 不出现漏光、闪烁、陈旧结果覆盖、并发异常或退出后残留线程；
- p99/max 明确改善，平均 FPS 下降不得超过噪声范围；
- 若正确性无法用小改动保证，停止实现并保留同步路径。

### 4.6 纹理加载临时数据优化

#### 目标

减少资源加载和纹理图集构建过程中的临时像素数组、mipmap 数据和复制成本，改善资源包切换卡顿。

Forge 1.8.9 的 `TextureUtil` 已经持有并复用一个静态 4,194,304-int direct buffer，普通 `uploadTextureSub` 不会为每次上传重新分配 direct buffer。因此不实现新的上传缓冲池。

#### 定价探针

- 纹理上传次数、字节数和单次/总耗时；
- `uploadTextureImageSubImpl` 的临时 `int[]` 分配量；
- mipmap 生成和图像像素提取耗时；
- 资源包加载、切换和动态图场景中的 GC 情况。

#### 第一版范围

- 若探针确认 `BufferedImage` 上传临时数组是显著来源，只复用该堆上 `int[]`；
- 保留原版静态 direct buffer 和分块上传逻辑；
- mipmap 或图像解码只有在各自 section 达到门槛后才单独立项；
- 不把资源加载优化宣传为游戏内平均 FPS 优化。

#### 验收

- 资源包加载、重复切换、动画纹理和超大贴图均无损坏；
- 临时数组分配显著减少，加载耗时或 GC 指标至少一项稳定改善；
- 可复用堆数组不得因一次异常资源永久保留过大内存。

## 五、低成本画质与内容裁剪

这些设置通过少绘制或降低资源精度换取性能，不应和同画面优化混为一谈。统一放在 Performance 模块的视觉裁剪分组，默认关闭并提供明确说明。

### 5.1 方块与实体隐藏

计划加入以下独立开关：

- `HideTallGrass`：隐藏高草；
- `HideDoubleTallGrass`：隐藏双高草；
- `HideFlowers`：隐藏花；
- `HideDoubleTallFlowers`：隐藏双高花；
- `HideFences`：隐藏栅栏；
- `HideFenceGates`：隐藏栅栏门；
- `HideSkulls`：隐藏头颅 block entity；
- `HideArmorStands`：跳过盔甲架实体渲染。

实现入口已经可以确定：

- 植被和栅栏在 `BlockRendererDispatcher.renderBlock` 的 HEAD 按 `IBlockState.getBlock()` 过滤并返回 `false`，只影响区块网格生成；
- 盔甲架在 `RenderManager.doRenderEntity` 的现有 HEAD 注入中按 `EntityArmorStand` 返回 `false`；
- 头颅在 `TileEntityRendererDispatcher.renderTileEntity` 的现有 HEAD 注入中按 `TileEntitySkull` 取消；
- 开关变化后仅触发必要的区块重建；
- 头颅和盔甲架只跳过渲染，不删除实体或 block entity；
- `HideArmorStands` 与现有只隐藏名称的 `IgnoreStands` 明确区分，避免用户误解；
- 所有选项默认关闭，并提示可能隐藏服务器标记、装饰或必要信息。

验收覆盖资源包模型、世界重载、运行中开关，以及栅栏连接/门开合后区块正确重建。

### 5.2 贴图分辨率限制（已实现，改为采样方案）

**原方案（缩放图片）已废弃。** 原计划提供最大边长档位并缩放图片，但 `TextureAtlasSprite.loadSprite` 按图片宽度解析动画帧数，缩放后每个动画贴图的帧布局都会被改写；而拦截 `TextureUtil.readBufferedImage` 又会连 GUI、字体、光照贴图和动态纹理一起误伤。这两个问题都无解，只要动的是像素。

**现方案：只动采样，不动像素。** `GL_TEXTURE_MIN_LOD` 在放大/缩小判定**之前**钳制 LOD，所以把下限设为 2，贴在镜头前的方块也会从 mip level 2 采样 —— 每档边长减半。图集本身完全不变：同样的图片、同样的拼接、同样的帧布局、同样的纹理对象。

这个方案还自带了原方案要靠过滤器维护的隔离性：方块图集是原版唯一带 mipmap 链分配的纹理（`TextureUtil.allocateTextureImpl(id, mipmapLevels, w, h)`），GUI、字体、光照贴图和动态纹理都是单层分配，**结构上**够不着 mipmap 设置。

档位为 `Default` / `Half` / `Quarter` / `Eighth` / `Sixteenth`，索引即 LOD 下限。命名按"相当于多少倍率的贴图"而不是像素数，因为同一档在 16x 和 512x 资源包上必须都成立。

实现要点：

- `TextureUtil.allocateTextureImpl` 只在图集分配时写一次 LOD 范围，`setTextureBlurMipmap` 只碰 MIN/MAG_FILTER，所以不需要每帧重设；但**资源重载会重新分配纹理并把 LOD 范围写回默认值**，因此在 `TextureMap.loadTextureAtlas` 返回处重新应用。
- 上限钳制到图集实际的 `mipmapLevels`，它不等于游戏的 Mipmap Levels 设置 —— `loadTextureAtlas` 在图集不是足够大的二次幂时会自行下调。
- 游戏的 Mipmap Levels 设为 0 时本功能无效（没有更粗的层可退），此时记一条日志，否则和功能坏掉无法区分。

验收记录截图差异、显存近似占用和资源重载后是否仍然生效；默认必须为 `Default`。

## 十、实体模型渲染（§4.7）

### 10.1 已知的事实

`ModelRenderer.render(scale)` 对每个 box 做：

```
translate(offsetX/Y/Z)
  [有旋转时] pushMatrix + translate(rotationPoint) + 最多三次 rotate
  callList(displayList)          ← 几何在局部坐标系，变换全部来自固定管线矩阵栈
  递归 childModels
  [有旋转时] popMatrix
translate(-offsetX/Y/Z)
```

实测：一个盔甲架约 12 个 box，`renderModel` **8.66us**，即每 box 0.72us。对一个平凡立方体而言，2200 个周期是荒谬的。

现有的 `BatchModelRendering` 批的是 `compileDisplayList` **内部**的顶点提交，**没有减少每帧 `callList` 的次数**。这一点已经在 `RESULTS.md` 写明。

本项目此前两次尝试的结果：`CacheModelLists` +0.4%（噪声内）、"整模型打包成单个显示列表" −5.00% 对 4.04% 噪声带（机制判断错误，已回退）。

### 10.2 假设，以及为什么不能直接照它做

**假设**：`glCallList` 在现代驱动上是被模拟的，所以每 box 一次 callList 就是每 box 一次模拟开销。

**证据强度**：本项目确实测过显示列表被模拟 —— `FontOptimize` 因此 −58% 帧率被删除。**但那是另一种使用模式**（每字形一个列表、每帧成百上千次调用），不能直接推广到每实体十二次。

**本轮已经有三次"先假设后验证"被证伪**：HUD 缓存（以为瓶颈在排版，实际排版只占五分之一）、地形遍历成因（以为是相机，实际是区块工作）、容器池化（以为分配是开销，实际占 4%）。**这一项不允许再犯第四次。**

### 10.3 阶段一：决定性探针（已完成，假设被推翻）

**结果**（`entity-dense-quick`，`entityModel` section CPU p50）：

| 变体 | entityModel | 相对基线 |
|---|---:|---:|
| 基线 | 135us | — |
| `noModelCallList`（保留变换，不画） | 99us | **−36us（−27%）** |
| `noModelTransforms`（保留画，不变换） | 62us | **−73us（−54%）** |

**矩阵运算是显示列表重放的两倍。** 站了很久的假设 —— "`glCallList` 被驱动模拟，所以每 box 一次 callList 就是主要开销" —— 是错的，而且错在方向上。

另外：每帧 1055 次 `callList`，`entityModel` 135us，即**每 box 128ns**。旧记录是 720ns。差异来自开发机的 CPU 性能调度被修正，**本轮之前所有的时间类基线都需要重测**。

所以走**路线 A**（合成变换、保留显示列表），它同时是改动小的那一个。

### 10.3.1 原始探针设计（保留作为方法记录）

用本项目既有的 ceiling probe 模式（`Experiments`：把工作直接删掉，看帧到底短了多少），加两个互补的开关：

| 探针 | 做什么 | 回答什么 |
|---|---|---|
| `-Dedge.exp.noModelCallList` | 跳过 `callList`，**保留**全部 translate/rotate | 列表重放本身值多少 |
| `-Dedge.exp.noModelTransforms` | 跳过 translate/rotate，**保留** `callList` | 固定管线矩阵运算值多少 |

外加计数器：每帧 `callList` 调用次数、每帧 box 数、有旋转的 box 占比。

**判据**：两个探针的收益之和应当接近 `renderModel` 的 8.66us/实体。若都接近零，则成本在别处（状态验证、纹理绑定、`RendererLivingEntity` 的外层），路线全部作废，重新定位。

场景用 `entity-dense`（120 个盔甲架），它是为这件事造的。

### 10.4 阶段二：按探针结果二选一

**若 `callList` 是主要成本 —— 路线 B：CPU 变换 + 每实体单批**

- 每个 box 的四边形在局部坐标系是**静止**的，把它们留在 CPU 侧的 `float[]`（`TexturedQuad` 已有顶点数据，`compileDisplayList` 现在就在遍历它们）
- 每帧对每个实体：遍历 box 树，在 CPU 上把 box 的变换（translate + 最多三次 rotate，可合成一个 3×3 + 平移）应用到顶点，**追加进同一个 `WorldRenderer` 批次**
- 一个实体一次 `Tessellator.draw()`，取代约 12 次 `callList` + 约 60 次矩阵调用

成本估算：12 box × 24 顶点 = 288 次顶点变换/实体，每次约 15 flop ≈ 4300 flop。**这个量级是否真的比 8.66us 便宜，由阶段一的数字决定，不由估算决定。**

**若矩阵运算是主要成本 —— 路线 A：合成变换，保留显示列表**

在 CPU 上把一个 box 到根的变换链合成为单个矩阵，用一次 `glLoadMatrix` 取代 push/translate/rotate×3/pop。几何不动，改动面小得多。

### 10.5 边界与失效条件

- 不跨实体合批：`RendererLivingEntity` 每实体设置亮度和颜色，图层还会重绑纹理。**只在单个实体内部合批。**
- 变换必须与固定管线**逐位一致**，否则模型会错位。验收用截图对比（`compare-shots.py`），不是看帧率 —— 模型少画或错位都会让帧率变好。
- 覆盖：玩家、盔甲架、掉落物、生物、盔甲图层、手持物图层、披风。任何一个走了不同路径的都必须回退到原版。
- 必须保留 `BatchModelRendering` 的开关语义：新路线是另一个开关，不是替换，两者可独立关闭。

### 10.6 验收

- `entity-dense` 与两段 Hypixel 录像上，`renderModel` section 显著下降，且**截图与原版一致**
- 三组交错配对，方向一致，区间不重叠（仪器已具备 0.9% 复现度）
- 性能监视 HUD 上 1% low 不劣化 —— 一个把成本从每帧摊平改为集中在某几帧的改动会赢在均值输在尾部

## 十一、原版字体批量绘制（§9.1 "HUD 文字第二期"的另一条路）

### 11.1 问题

`CustomHudFont` 是本项目单项收益最大的开关，但默认关着，原因不是性能而是**字形不是 Minecraft 的**。愿意换帧率的人已经开了；不愿意的人一直在付原版的全价。

原版的价格来自 `FontRenderer.renderDefaultChar`：

```java
this.bindTexture(this.locationFontTexture);
GL11.glBegin(5);                       // GL_TRIANGLE_STRIP
GL11.glTexCoord2f(...); GL11.glVertex3f(...);   // x4
GL11.glEnd();
```

**每个字符**一次 bind + 一次 `glBegin`/`glEnd`。一屏繁忙 HUD 是几千次立即模式提交。

### 11.2 Badlion 做了什么（结论：这条路他们没走）

从 `tools/dumper-agent/out` 反编译确认三件事：

1. **他们没有优化原版逐字符路径。** `avn`（= `FontRenderer`）的 `renderDefaultChar` 依旧是每字符 `glBegin(5)`，和原版逐行一致。
2. **他们在字符串层拦截并回退**，与本项目 `CustomHudFont` 同构：

   ```java
   int var6 = db.customFontManager.drawMCString(var2, var3, var1, var4);
   if (var6 != -1) return var6;   // 自定义字体接管
   else { ...原版逐字符路径... }
   ```

3. **他们的字体不是原版风格，也不兼容原版贴图与材质包。** `KN`（CustomFontManager）import `com.mlomb.freetypejni`，运行时用 FreeType 栅格化真实 TTF／系统字体（日志 `[CustomFontManager] Found N system font files`），自建图集走 GL15/GL20/GL30 的 VBO 路径，与 `textures/font/ascii.png` 无关。

附带发现一个方向相反的功能：`aox.aca()` 绕过材质包，直接从 `getMcDefaultResourcePack()` 读原始 `ascii.png` 上传成独立纹理，配合 `net.badlion.clientcommon.util.h.k(char)` 的硬编码宽表；`abZ()` 才是走材质包的 `locationFontTexture`，由 `usesVanillaFont()` 二选一。这是"强制默认字体、无视材质包"，与性能无关。

**所以批量化原版字体没有现成先例可抄。**

### 11.3 方案

`VanillaFontBatch` + `FontRendererMixin_BatchVanilla`：把 `renderDefaultChar` / `renderUnicodeChar` 的四个顶点原样写进一个共享的 `POSITION_TEX` 批次，每条字符串结束时提交一次。

**顶点常量逐个对照过原版**（`7.99F`、`0.01F`、`0.02F`、`15.98F` 是它的溢出防护，动一位小数就改变边缘采样的 texel）。唯一的改动是把三角带顺序改写成四边形绕序 —— 原版第三、四顶点是另一条对角线，照抄进 `GL_QUADS` 会把字形折叠。

三处必须提前提交：

| 触发 | 原因 |
|---|---|
| 页切换 | 一个批次只有一张纹理 |
| `setColor` | 批次不带逐顶点颜色 |
| `doDraw`（仅删除线/下划线开启时） | 它用同一个 `Tessellator` 画线，会和打开的批次撞车 |
| `renderStringAtPos` 返回 | 留到下一条会被用错颜色画出来 |

`flush()` 同时清掉记住的页：两条字符串之间任何代码都可能 bind 别的纹理，沿用缓存等于跳过一次已经不成立的 bind。代价是每条字符串一次 bind —— 原版是每字符一次。

### 11.4 Mixin 环境注意

`setColor`、`doDraw`、`bindTexture` 是 Forge 补丁加进 `FontRenderer` 的，**没有 SRG 映射**，必须 `remap = false`；`@Inject` 会直接编译报错，`@Shadow` 只警告然后在运行时静默失效。`loadGlyphTexture` 同样解析不到，改为在 mixin 内自己缓存 `unicode_page_%02x.png` 的 `ResourceLocation`。

### 11.5 结果：像素过关，收益接近零

**像素**：同一系列内 on 对 off，三张截图在第一人称手臂之外**差异像素为 0**。计分板、物品栏逐位相同，顶点数学验证无误。

**收益**：两版实现，`text-dense` 三轮交错（完整数字见 `RESULTS.md`）：

| 实现 | `hud` p50 off | `hud` p50 on |
|---|---|---|
| 收集进 `WorldRenderer` | 49–50us | **64–65us（+30%，反向）** |
| 立即模式，只把 `glBegin`/`glEnd` 提到字符串级 | 49–50us | 48us（−2.7%） |

第一版为什么是反向的，值得记住：**mixin 的逐字符注入回调在 off 侧同样执行、同样分配 `CallbackInfoReturnable`，那份开销已经在基线里**，所以多出来的 15us 只能是收集本身 —— `pos().tex().endVertex()` 每顶点的偏移算术加容量检查，四顶点一字形，比省掉的 `glBegin`/`glEnd` 还贵。

两个数一起读出结论：**每字符一对 `glBegin`/`glEnd` 在这台驱动上约 3ns/字形，几乎免费。** 原版字体的成本不在批量化能拆的地方。

`BatchVanillaFont` 保留、默认关（正收益、像素一致、不引入新失效模式，但 1.3us 不值得在聊天／GUI／告示牌／书本这些同走 `FontRenderer` 的路径实机验证前默认打开）。

### 11.6 盘子有多大，以及剩下的成本在哪

`replay-pit` 上量 `CustomHudFont` off/on（三轮，区间不重叠）：`hud` **224/235/229us → 183/177/179us**，
即 **−50us / −21.7%**，约占 763us 整帧的 6.5%。批量化拿到的 1.3us 只占其中 2.6%。

剩下的 48us 是读原版源码找到的，不是猜的：`FontRenderer` 用 `indexOf` 在一个 **256 字符**常量串里
找字形位置，**三个调用点全是每字符一次** ——

| 位置 | 频率 |
|---|---|
| `renderStringAtPos` | 每渲染字符一次（决定阴影偏移） |
| `renderChar` | 每渲染字符一次，粗体再一次（选默认页还是 unicode 页） |
| `getCharWidth` | 每**测量**字符一次 —— `getStringWidth` 逐字符调它，HUD 为了居中／右对齐几乎对每条串都测一遍 |

画一个字符至少两次 256 长度线性扫描，量一个字符再加一次。**成本在 CPU 侧的查找，不在 GL 调用上**，
这与 11.5 的结论互为佐证。

## 十二、字形查表（`FastGlyphLookup`）

`FontRendererMixin_GlyphIndex` 把那三处 `indexOf` 重定向到一张按字符索引的 `short[]`。返回值与原版
逐个相同，只是找法不同 —— 所以选中的字形和量出的宽度都不变。

**查表在运行时从接收者自身构建、按引用识别**：那个常量在 `FontRenderer` 字节码里是内联字面量，
1.8.9 没有字段持有它（`ChatAllowedCharacters` 暴露的 `char[]` 是另一个集合），把 256 个制表符和
带音标拉丁字母抄进源文件是白担一份正确性风险。`renderStringAtPos` 里还有一处 22 字符的颜色码
`indexOf`，按长度区分走原路。倒序填表，因为 `indexOf` 返回首次出现而那个串里有重复的 NUL 填充。

### 12.1 结果

| `replay-pit`（长系列，三轮） | off | on |
|---|---:|---:|
| `hud` p50 | 223, 226, 229 us | **202, 194, 201 us（−27us，−11.9%）** |

区间不重叠。对照上面 50us 的差值：**查表一项拿回 54%，画面不变。**

| `text-dense-quick`（五分钟档，各一轮） | 两项全关 | 两项全开 |
|---|---:|---:|
| `hud` p50 | 50 us | **38 us（−24%）** |

**像素**：三张截图的差异像素全部落在第一人称手臂区域，文字区域为 0。

**默认开**，因为它只删工作不加工作，且不付出 Minecraft 观感的代价。

### 12.2 尚未验证

两项都**没有在真实客户端里跑过**。聊天、GUI 界面、物品提示、告示牌、书本全都走 `FontRenderer`，
`replay-pit` 和 `text-dense` 覆盖的只有计分板、玩家列表和物品栏。上线前需要实机走一遍这些路径。

## 十三、HUD 文字提交合批（存档思路，未实施）

**性价比不足，暂不做。** 记在这里是因为分析已经做完，丢掉可惜。

### 13.1 问题

`TextRenderer.drawCached()` 每条字符串一次 `Tessellator.draw()`。pit 上 40–47 条/帧，bedwars 51–71 条/帧。

### 13.2 成本在字符串条数，不在顶点

有一个不依赖任何拟合的交叉观察：

| | 字形四边形 | 字符串 | `text:submit` |
|---|---:|---:|---:|
| pit | 592–790 | 40.0–47.4 | 59.9–65.0 us |
| bedwars | 355–698 | 51.4–70.6 | **68.9–75.1 us** |

**bedwars 的顶点比 pit 少 24%，提交成本却高 15%。** 顶点解释不了这个方向，字符串条数可以。

两组中位数反解（两场景两未知数，**两点拟合，不是测量值**）：每条字符串 0.88us，每顶点 8.7ns；
pit 上字符串占 62%，bedwars 占 75%。

`text:setup` 这个 bracket 已经把状态设置单独计过（pit 4.2–4.5us / 40–47 条 ≈ **0.1us 每条**），
所以那 0.88us 几乎全在 `Tessellator.draw()` 本身 —— 驱动侧指针设置、客户端状态开关、
`glDrawArrays`，约 3000 周期。

### 13.3 方案与障碍

不能简单地把批次开着跨字符串：计分板是「背景矩形、一行字、再一条矩形」交替，而矩形走**同一个**
`Tessellator`，批次每行都会被打断。

要用**自己的持久 direct ByteBuffer**，不共用 `Tessellator`：自己的
`glVertexPointer`/`glTexCoordPointer`/`glColorPointer` + `glDrawArrays`；每条字符串按 origin 偏移
追加、不画；整个 HUD 结束时一次 `glDrawArrays`；只有图集 generation 变化才中途 flush。

**代价是 z 序** —— 所有文字被推迟到最后画。计分板那种「每行字在自己背景之上、背景互不重叠」的
结构推迟后视觉相同，但如果有 HUD 元素本该盖住文字就会露出来。必须靠 `text-dense` 的像素闸门守。

**预期**：pit 38.5us、bedwars 53.7us 中的大部分，约整帧 5–7%。

### 13.4 动手前必须先做的探针

上面的分解是两点拟合，而本轮已经在字体成本位置上错过一次。把 `text:submit` 拆成 `write`
（顶点循环）和 `draw`（`Tessellator.draw()`）两个 bracket，跑一次就知道 0.88us 是不是真在 draw 里。

### 13.5 前提

只在 `CustomHudFont` 开启时有效。默认关闭时 `TextRenderer` 每帧只画 3 条字符串。


## 十四、字体工作收尾

### 14.1 交付了什么

| 开关 | 收益 | 画面 | 默认 |
|---|---|---|---|
| `FastGlyphLookup` | `replay-pit` `hud` **−27us / −11.9%**，长系列三轮区间不重叠 | 逐位一致 | **开** |
| `MergeTextShadow` | `text-dense-quick` `hud` **−4~−6us**，两轮独立复现；`replay-pit` 总 draw call −23% | HUD 文字逐位一致 | **开** |
| `BatchVanillaFont` | `text-dense` `hud` −1.3us | 逐位一致 | 关 |
| `SlowObfuscation` | 机制成立（命中率 98.0%），**收益未证实**（配对受扰） | **改变**（20Hz vs 帧率） | 关 |

起点是"原版字体能否达到自定义字体的性能水平"。`replay-pit` 上量出的差值是 `hud` **−50us**；
`FastGlyphLookup` 一项拿回 54%，`MergeTextShadow` 与 `BatchVanillaFont` 各自再补一点。**剩余差值
约 20us**，且 `MergeTextShadow` 同时也让自定义字体那条路更快，所以差值不会被完全抹平。

### 14.2 三个被推翻的假设

按顺序，全部是先测才发现的：

1. **以为成本在每字符的 `glBegin`/`glEnd`。** 第一版批量化（收集进 `WorldRenderer`）`hud` 从 50us
   涨到 65us；改成立即模式只把括号提出循环后是 −1.3us。结论：那对括号在这台驱动上约 3ns/字形。
2. **真正的成本是每字符三次 256 长度线性扫描**（`renderStringAtPos`、`renderChar`、`getCharWidth`），
   读源码找到的。换成一次数组读 = −27us。
3. **以为阴影只能画两遍。** `record()` 里 `shadowPass` 只影响颜色，几何完全相同 —— 一条带阴影的
   字符串原本存着两份一模一样的几何。

### 14.3 `SlowObfuscation` 的悬案

命中率 98.0% 是计数，成立无疑；但 `hud` 测出 +5us，而那一对 avg fps 差 21%、p99 双双 13–14ms，
是机器受扰的特征。按早前探针推算应当是 −11us。**两个数字矛盾且没有第三次运行来分辨。**

它是四个开关里唯一改画面的，天花板又随服务器的混淆文字量变化（这段录像每帧 9.2 条）。
所以：保持默认关，要么补一次长系列定案，要么连设置项一起删掉。**不要在没有数字的情况下把它打开。**

### 14.4 未验证（上线前必须补）

**四个开关都没有在真实客户端里跑过。** 聊天、GUI 界面、物品提示、告示牌、书本全部走
`FontRenderer`，而 `replay-pit` / `text-dense` 只覆盖计分板、玩家列表和物品栏。

`MergeTextShadow` 的风险点具体是：它挂在 `drawString` 上并取消整个方法，`resetStyles()` 的语义
是手工复刻的（`@Shadow` 那五个样式字段），回落到原版渲染器的路径（bidi 文本、银河文字）没被
任何场景覆盖过。


## 十五、判据：一个优化能不能兑现

本轮反复撞到的两条，写下来省得下次再花一轮发现。

### 15.1 降低几何量 vs 其他一切

两个测试场景在 1280×720 下**都是几何提交受限**（把像素砍到四分之一，GPU 时间不变）。在这个条件下：

| | 结果 |
|---|---|
| 让 CPU 更快地把工作交出去（`CacheItemModels`） | CPU −15%，GPU 不变，**帧率不动** |
| 根本不把工作交出去（`EntityCulling`） | GPU −18.6%，**帧率 +24.3%** |

后来用「三角形不变、draw call 翻倍」的探针把提交量再拆了一层，结论要收紧：

| 改动 | 结果 |
|---|---|
| 砍掉一半地形（draw + 三角形） | +26% |
| **draw call 翻倍（三角形不变）** | **0** |
| `EntityCulling`（整只实体不画） | +24% |
| `CacheItemModels`（同样几何、更快提交） | 0 |

**能兑现的是减少几何量，不是减少 draw call 数量。** `EntityCulling` 有效是因为它连同三角形删掉实体。这条直接关闭 Render Regions 这一类"合并绘制"的方向。

**先看 GPU 计时 —— 但只看 `frameTotal`。** 如果 GPU ≥ CPU，只降 CPU 提交成本的优化无法兑现。细粒度 section 的 GPU 数字不可用（见 §21 记录：紧贴 `drawArrays` 的 bracket 报 0，而删掉那些绘制省 377us），归因要用天花板探针。

### 15.2 自适应开关要两个信号，不是一个

`EntityCulling` 的守门条件从"实体数量 ≥ 24"改成遮挡率驱动的状态机，然后在真实 PvP 上亏了 4.5%：
遮挡率 65.5% 说"有东西被挡住"，但每帧只藏住 2.36 个实体，付不起探针。

| 信号 | 回答 | 单独用的失败方式 |
|---|---|---|
| 遮挡率 | 有东西被挡住吗 | 少量实体高遮挡率 → 进入剔除态然后亏 |
| 实体数量 | 有足够成本值得回收吗 | 数的可能全在明处 → 该剔的场景被挡在门外 |

**用两者的乘积：每次 sweep 实际藏住的绝对数量。** 它直接量的就是省下来的东西。
