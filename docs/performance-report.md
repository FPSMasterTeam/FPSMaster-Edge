# 性能优化 campaign 收尾报告

覆盖 2026-07-26 至 08-01，47 个 `perf`/`fix` 提交，`RESULTS.md` 2386 行原始记录。

这份报告只写**实测支撑的结论**。没有数字的判断一律标注为未验证。

## 一、交付了什么

### 1.1 默认开启（13 项）

| 开关 | 实测收益 | 场景 |
|---|---|---|
| **`EntityCulling`** | **fps +24.3%，GPU −18.6%** | 装饰实体密集且有遮挡 |
| **`FastGlyphLookup`** | `hud` **−27us / −11.9%**，三轮区间不重叠 | 全场景 |
| **`MergeTextShadow`** | `hud` −4~−6us，draw call −23% | 带阴影文字 |
| **`FastTextureUpload`** | 加载期上传 **160–183ms → 36.5ms** | 加载/资源包切换 |
| **`ReuseVisibleChunks`** | 地形遍历 −33~44%（约 265us/帧，CPU 侧） | 全场景 |
| `LimitChunks` + `ChunkUpdateLimit` | 关掉 fps −7.3% | 全场景 |
| 其余 7 项 | 早期实测，本轮未重测 | — |

### 1.2 默认关闭且有明确理由

| 开关 | 实测 | 为什么关 |
|---|---|---|
| `CacheItemModels` | `entityLayers` −46%（四次复现） | **收益从未到达帧时间**，见 §3.2 |
| `CullPlayers` | **−4.5%**（真实 PvP，十段九段一致） | 实测负收益 |
| `ComposedModelTransform` | `entityModel` −10.5%，fps +2.7% | 小，且未实机验证 |
| `BatchVanillaFont` | `hud` −1.3us | 太小 |
| `SlowObfuscation` | 命中率 98%，时间不可用 | 改画面且收益未证实 |
| `AdaptiveChunkBudget` | 与固定预算区间重叠 | 未胜出 |
| 23 项「隐藏内容」旋钮 | — | **删画面而不是让同样的画面更快** |

## 二、被推翻的假设

**每一条都是先测才发现的，而且当时都有一个看起来合理的相反直觉。**

| # | 原假设 | 实测 |
|---|---|---|
| 1 | HUD 成本在布局 | 在**顶点提交**；可复用内容占 99.7% |
| 2 | 地形重建的触发是相机移动 | 是**区块工作** |
| 3 | `ContainerLocalRenderInformation` 分配值得池化 | 仅占遍历 **4%**，写代码前放弃 |
| 4 | 模型渲染的成本在 `glCallList` 模拟 | **变换是它的两倍** |
| 5 | 原版字体慢在每字符 `glBegin`/`glEnd` | 那对括号约 **3ns/字形**；成本在每字符**三次 256 长度线性扫描** |
| 6 | 实体图层的大头是盔甲 | **手持物占 59%（4.2us/件），盔甲 26%（0.46us/件）—— 一把剑抵九件盔甲** |
| 7 | 减少 draw call 能提速 | **draw call 翻倍代价为零**；成本全在三角形 |
| 8 | 加载优化里上传最值得做 | 上传占图集构建 **5%**，拼接器占 **67%** |

第 5 条和第 6 条各自推翻了一个已经**写完代码**的方案。

## 三、两条可复用的判据

### 3.1 能兑现的是减少几何量

| 改动 | 结果 |
|---|---|
| 砍掉一半地形（draw + 三角形） | **+26%** |
| draw call 翻倍（三角形不变） | **0** |
| `EntityCulling`（整只实体不画） | **+24%** |
| `CacheItemModels`（同样几何、更快提交） | **0** |

**减少 draw call 数量或提交成本都不兑现，减少三角形才兑现。** 这条直接关闭了 Render Regions
一类「合并绘制」的方向。

### 3.2 GPU 受限时 section 计时会骗人

`CacheItemModels` 让 CPU section 降 13.5%，帧率纹丝不动，GPU 时间不变 —— 省下的 CPU 无处兑现。
**profiler 的 section 收益在驱动受限时可能是阻塞位移而非工作消失，而 section 计时分不出这两者。**

更强的版本：紧贴 `drawArrays` 的 GPU bracket 报 **0**，而删掉那些绘制省 **377us**。
**归因 GPU 成本只能用天花板探针**，不能用 bracket。

## 四、仪器：修了什么，还剩什么

### 4.1 已修（每一次都立刻改变了结论）

| 修复 | 效果 |
|---|---|
| 回放窗口锚定录像位置 | 同配置两轮负载差 **26% → 0.03%** |
| 镜头路径随窗口重启 | 静止场景负载差 **10% → 0%** |
| `trace.py` 逐帧序列比较 | 自动核对天花板探针「假设不变」的负载 |
| GPU 计时报采样覆盖率 | 把「真的是 0」和「没测到」分开 |
| 加载阶段墙钟计时 | 让一整类工作第一次可测 |
| 五分钟档 + 像素闸门 | 单次验证 275s |

### 4.2 未修

- **GPU 归因** —— 细粒度 bracket 不可用（原因已查明并固化进 `GpuTimer` 注释，加更多 bracket 无用）
- **加载耗时轮间方差 14%**，且加载只发生一次，无法轮内交错对照
- 稳态检测器偏弱，九次约一次放行
- 五分钟档对 `terrainSetup`／整帧不可用（噪声地板 32%／21%）

### 4.3 一个跨越整个 campaign 的污染

**这个 campaign 横跨两块 GPU**：07-28 之前 391 次运行在 NVIDIA RTX 5060（独显），之后 229 次在
AMD Radeon 610M（核显）。两者瓶颈不同。

`Render Regions` 的否决依据来自独显（122.6 draw call/帧），当前机器是 444.4。**重测之后结论
仍然成立，但依据换了。** §9.4 里其余依赖独显数据的否决**没有重测**。

## 五、方法论：三次「功能没跑」

`CacheItemModels` 第一版（tint 判断拒了所有 2D 物品）、`EntityCulling` 在 pit 上（实体数低于
阈值，探针一次没发）、`MergeTextShadow` 前两次验证（场景里 0 条带阴影字符串）。

**每一次在时间和像素上都与「功能没用」完全同形，每一次都是计数器分开的。**

如果只看时间，第一条会显示 `entityLayers` 723 vs 726 —— 一个漂亮的「没有收益」，然后整条路
就废了。

**推论**：任何新功能都要先加一个「它跑了吗」的计数器，再看它的时间。
